# Smoke-тест TlibWebApp через MCP Playwright

## Каталог тестов проекта

Этот файл — центральный оркестратор тестирования TlibWebApp. Ниже — полная карта всех тестов.

### MCP интерактивные тесты (этот файл)
- **15 тестов:** Visual (5) + UX (5) + Exploratory (3) + Accessibility (2)
- Выполняются через MCP Playwright в чат-сессии
- Проверяют то, что автоматизированные тесты не могут: визуальное качество, UX, нестандартное поведение

## Цель и правила выполнения

**Эти тесты проверяют то, что автоматизация не умеет:**
- Визуальное качество рендеринга (пиксели, вёрстка, читаемость)
- UX-эвристики (понятность, консистентность, feedback)
- Нестандартное поведение при неожиданных действиях
- Доступность и навигация с клавиатуры

**Принципиальное отличие от E2E-тестов:**
- Каждый тест использует `browser_take_screenshot` для визуальной оценки
- AI оценивает скриншот глазами, а не через DOM-атрибуты
- Нет проверок типа «элемент существует» — это уже делает Playwright

**Правило остановки:**
- При явном крэше приложения — останови и сообщи
- При визуальных проблемах — зафиксируй как FAIL и продолжай

**Стратегия ожидания (важно для агента):**
- Предпочитаемый способ: `browser_wait_for` с параметром `text` или `textGone` вместо фиксированного таймера
  - Ждать окончания инициализации: `browser_wait_for textGone="Загрузка..."`
  - Ждать появления таблицы: `browser_wait_for text="Найдено"`
  - Ждать загрузки карточки: `browser_wait_for text="Маршрут:"`
  - Ждать результата поиска (в т.ч. пустого): `browser_wait_for text="Найдено"` или `browser_wait_for text="Ничего не найдено"`
- Если нужна фиксированная пауза: параметр `time` задаётся в **секундах** (не миллисекундах!): `time: 2` = 2 секунды
- Для проверки готовности страницы перед действием использовать `browser_snapshot`

## V1. Главная страница — визуальная целостность

**Категория:** Visual
**Инструмент:** `browser_take_screenshot`

**Действия:**
1. `browser_resize` на 1920x1080
2. `browser_navigate` на `https://your-server.example.com`
3. `browser_wait_for` с `textGone="Загрузка..."` — дождаться окончания инициализации
4. `browser_take_screenshot`

**AI оценивает:**
- Ни один элемент не перекрывает другой
- Шрифты рендерятся чётко (нет размытия, неправильного начертания)
- Нет артефактов: белых полос, сдвинутых блоков, "поехавших" колонок
- Форма поиска визуально читаема как единый блок
- Цветовая схема выглядит целостно, нет случайных цветных пятен

**PASS если:** страница выглядит законченно, все элементы на своих местах, текст читаем
**FAIL если:** видны наложения элементов, артефакты рендеринга, нечитаемый текст

## БЛОК 2: UX-эвристики (U1–U5)

## U1. Видимость состояния системы

**Категория:** UX
**Инструмент:** `browser_take_screenshot`, `browser_snapshot`

**Действия:**
1. `browser_navigate` на `https://your-server.example.com`
2. `browser_wait_for` с `textGone="Загрузка..."` — дождаться инициализации, затем сразу нажать "Найти"
3. `browser_take_screenshot` (сразу после клика, пока идёт загрузка)
4. `browser_wait_for` с `text="Найдено"` — дождаться результатов
5. `browser_take_screenshot` (после загрузки)

**AI оценивает:**
- Есть ли визуальный индикатор, что поиск выполняется (спиннер, прогресс-бар, изменение кнопки)?
- После завершения поиска — понятно ли пользователю, что результаты загружены?
- Кнопка "Найти" меняет состояние (disabled, текст, иконка) во время поиска?
- Нет ли момента "завис экран" когда непонятно, что происходит?

**PASS если:** пользователь в любой момент понимает, что система делает
**FAIL если:** нет никакого индикатора загрузки, кнопка не реагирует, непонятно завершился ли поиск

## U2. Предотвращение ошибок

**Категория:** UX
**Инструмент:** `browser_take_screenshot`, `browser_snapshot`

**Действия:**
1. `browser_navigate` на `https://your-server.example.com`
2. Попробовать ввести буквы "abc" в числовое поле "Шифр" (`input[name="Шифр"]`)
3. `browser_take_screenshot`
4. Очистить поле, ввести "9999" в поле "Год с"
5. `browser_take_screenshot`
6. `browser_snapshot` — зафиксировать значение поля

**AI оценивает:**
- Числовое поле "Шифр": принимает ли буквы? Как реагирует (блокирует, показывает ошибку, молча игнорирует)?
- Поле "Год с" с нереалистичным годом: есть ли валидация или подсказка?
- Способствует ли интерфейс предотвращению ошибок, или позволяет вводить что угодно без обратной связи?

**PASS если:** поля с ограниченным форматом блокируют или явно сигнализируют о неправильном вводе
**FAIL если:** числовые поля принимают любой текст без какой-либо обратной связи

## U3. Консистентность интерфейса

**Категория:** UX
**Инструмент:** `browser_take_screenshot`

**Действия:**
1. `browser_navigate` на `https://your-server.example.com`
2. `browser_take_screenshot` (форма поиска, сохранить как "экран А")
3. `browser_navigate` на `https://your-server.example.com/?1-TST`
4. `browser_wait_for` с `text="Маршрут:"` — дождаться загрузки карточки
5. `browser_take_screenshot` (карточка отчёта, сохранить как "экран Б")
6. Нажать на таб PDF
7. `browser_take_screenshot` (PDF-таб, сохранить как "экран В")

**AI оценивает:**
- Кнопки одного типа (primary, secondary) выглядят одинаково на всех экранах
- Шрифты единообразны: не смешиваются разные гарнитуры без смысла
- Цветовая схема последовательна на всех трёх экранах
- Иконки одного стиля (все outline или все filled, не смесь)
- Отступы и выравнивание ощущаются как единая система

**PASS если:** приложение выглядит как единый продукт, а не набор несвязанных страниц
**FAIL если:** заметны очевидные несоответствия в стиле между разными экранами

## U4. Помощь и ориентация пользователя

**Категория:** UX
**Инструмент:** `browser_take_screenshot`, `browser_snapshot`

**Действия:**
1. `browser_navigate` на `https://your-server.example.com`
2. `browser_take_screenshot` (форма поиска)
3. `browser_snapshot` — зафиксировать placeholder-ы полей
4. `browser_navigate` на `https://your-server.example.com/?1-TST`

**AI оценивает:**

- Новый пользователь поймёт основной сценарий работы за 30 секунд?

**PASS если:** интерфейс самодокументирован: пользователь понимает что делать без внешней помощи
**FAIL если:** ключевые поля непонятны, нет подсказок, основной сценарий неочевиден

## U5. Сообщения об ошибках — качество

**Категория:** UX
**Инструмент:** `browser_take_screenshot`

**Действия:**
1. `browser_navigate` на `https://your-server.example.com`
2. Ввести "99999" в поле "Шифр", нажать "Найти"
3. `browser_wait_for` с `text="Ничего не найдено"` — дождаться ответа
4. `browser_take_screenshot` (сообщение "Ничего не найдено")
5. `browser_navigate` на `https://your-server.example.com/doc.aspx?id=999999999`

7. `browser_take_screenshot` (страница с несуществующим отчётом)

**AI оценивает:**
- Сообщение "Ничего не найдено" — дружелюбное или холодное/техническое?

- Нет ли технических деталей (стектрейс, SQL-ошибки, пути к файлам) в сообщениях?
- Тон сообщений соответствует ожиданиям от библиотечного сервиса?

**PASS если:** сообщения понятны, дружелюбны, не содержат технического жаргона
**FAIL если:** видны технические ошибки, сообщения холодные/непонятные, нет подсказок

**PASS если:** приложение принимает любой текст без визуального краша или ошибок сервера
**FAIL если:** страница ломается, layout "едет", видна ошибка 500

## A1. Читаемость при увеличении масштаба

**Категория:** Accessibility
**Инструмент:** `browser_take_screenshot`, `browser_resize`

**Действия:**
1. `browser_resize` на 1920x1080
2. `browser_navigate` на `https://your-server.example.com`
3. `browser_take_screenshot` (базовый viewport 1920x1080)
4. `browser_resize` на 1280x720 — имитация zoom 150% (контент 1920px в уменьшенном viewport)
5. `browser_take_screenshot` (имитация масштаба 150%)
6. `browser_resize` на 960x540 — имитация zoom 200% (контент 1920px в ещё меньшем viewport)
7. `browser_take_screenshot` (имитация масштаба 200%)
8. `browser_resize` на 1920x1080 — вернуть исходный размер

**AI оценивает:**
- При viewport 1280x720: текст читаем, нет наложений, форма поиска целостна
- При viewport 960x540: принципиальная читаемость сохранена (допустим горизонтальный скролл)
- Контраст текста и фона достаточен для людей с пониженным зрением
- Нет элементов с очень мелким текстом даже при базовом масштабе (< 11px)
- Интерактивные элементы (кнопки, ссылки) остаются кликабельными при уменьшении viewport

**PASS если:** при viewport 1280x720 интерфейс пригоден для работы без горизонтального скролла
**FAIL если:** при 1280x720 элементы накладываются, текст нечитаем, кнопки недоступны

## A2. Keyboard navigation

**Категория:** Accessibility
**Инструмент:** `browser_take_screenshot`, `browser_press_key`, `browser_click`

**Действия:**
1. `browser_navigate` на `https://your-server.example.com`
2. `browser_wait_for` с `textGone="Загрузка..."` — дождаться окончания инициализации
3. `browser_click` на поле "Маршрут" — установить фокус на первое поле формы
4. `browser_take_screenshot` (первый фокус виден?)
5. Нажать Tab 5 раз подряд (`browser_press_key` с key: "Tab" × 5)
6. `browser_take_screenshot` (фокус перемещается по полям)
7. Перейти к полю "Год с", ввести "2024"
8. Нажать Tab до кнопки "Найти", нажать Enter (`browser_press_key` с key: "Enter")
9. `browser_wait_for` с `text="Найдено"` — дождаться результатов
10. `browser_take_screenshot`

**AI оценивает:**
- Видно ли визуально, какой элемент в фокусе (focus ring)? Достаточно ли он заметен?
- Порядок обхода по Tab логичен: форма сверху-вниз, затем кнопки?
- Можно ли отправить форму клавишей Enter (без мыши)?
- Нет ли "ловушек" Tab (фокус зацикливается на одном элементе)?

**PASS если:** форма полностью управляема с клавиатуры, focus ring чётко виден
**FAIL если:** focus ring отсутствует или невидим, Tab-порядок хаотичен, Enter не отправляет форму

## Диагностика при FAIL

Если тест завершился с FAIL, важно понять первопричину.

### Разграничение

| Тип проблемы | Что происходит |
|---|---|
| **Визуальный баг** | Рендеринг сломан: наложения, артефакты, неправильный размер |
| **UX-проблема** | Функционально работает, но пользователю непонятно или неудобно |
| **Краш** | Приложение не реагирует, ошибка 500, пустая страница |
| **Таймаут** | Приложение медленнее, чем ожидает тест |

### Шаги диагностики

**1. Зафиксировать скриншот при падении**

Описать в отчёте что именно видно на скриншоте: элементы, наложения, тексты ошибок.

**2. Проверить консоль на ошибки**

```
browser_console_messages
```

(вывод содержит все уровни; отфильтровать строки с `error` вручную в ответе)

**3. Изолировать проблему**

- Повторить действие с более медленным темпом (добавить `browser_wait_for` между шагами)
- Проверить, воспроизводится ли на desktop при нормальном масштабе

**4. Разграничить визуальный баг и функциональный**

Если элемент виден в `browser_snapshot`, но выглядит неправильно на скриншоте — это визуальный баг, не функциональный. Автоматизированные тесты его не поймают.
