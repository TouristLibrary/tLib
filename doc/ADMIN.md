Ежедневные операции, мониторинг и обслуживание TlibWebApp.

## Ежедневные операции

### Загрузка отчёта через сайт (/upload.html)

Основной способ для библиотекарей — страница загрузки `/upload.html` (вход по Magic Link).

**Кто что может:**
- **Любой авторизованный** пользователь заполняет форму (Маршрут, Год, Шифр-ДопШифр и пр.), прикладывает файл (ZIP или PDF, до 2 ГБ) и отправляет. Отчёт попадает в `data.up/10_up` (на рассмотрение), а всем администраторам уходит письмо «Загружен новый отчёт». По умолчанию код подставляется как `N-TLIB` (первый свободный N); поле проверяет уникальность Шифр-ДопШифр на лету.
- **Администратор** на той же странице видит таблицу отчётов «на рассмотрении». По строке:
  - иконка скачивания — забрать приложенный файл из `10_up` для проверки;
  - клик по строке — открыть форму редактирования полей + поле «Комментарий администратора»;
  - **Опубликовать** — правки сохраняются, пара json+файл переносится в `data.up/20_go`, дальше отчёт обрабатывает File Watcher (см. ниже). Письмо загрузившему («опубликовано») уходит **после** реальной публикации в `data/`;
  - **Отклонить** — пара уходит в `data.old/` с timestamp + создаётся `.err` с комментарием, загрузившему **сразу** уходит письмо об отклонении.

Под формой находится чек-бокс **«Не отправлять письмо загрузившему»** (по умолчанию снят). При установке чек-бокса письмо не отправляется ни при публикации, ни при отклонении. Чек-бокс сбрасывается при каждом открытии формы.

Сразу под таблицей «на рассмотрении» — раздел **«Скрытые отчёты»**: текстовое поле со списком `Шифр-ДопШифр` (через `;`, `,` или пробел/перенос строки) и кнопка **«Сохранить»** (активна только если текст изменён). Скрытый отчёт остаётся в результатах поиска как обычно, но на его странице показывается только карточка с описанием и плашка **«Отчет временно недоступен»** — файл не кешируется и не отдаётся вьюером/скачиванием. Пустой список означает «скрытых отчётов нет». Подробности: [API: скрытые отчёты](details/API.md#get-apiadminhidden-reports).

Комментарий администратора нигде в БД не сохраняется — он только уходит в письмо загрузившему.

Администратор также видит блок **«Загрузивший отчёт»** (скрытый от обычных пользователей): поле **E-mail** — единственное редактируемое; **Имя** и **ID** — только для чтения, заполняются автоматически по найденному в `auth.db` пользователю. При вводе e-mail и уходе с поля выполняется поиск по `auth.db`: если пользователь найден, имя и ID подставляются автоматически; если нет — под полем появляется сообщение об ошибке и кнопка сохранения блокируется. Очистка e-mail обнуляет `ЗагрузилID` в JSON отчёта (поле `ЗагрузилИмя` не затрагивается). Блок отображается во всех режимах формы, включая новую загрузку (предзаполнен текущим пользователем).

**Валидация формы загрузки (на клиенте):** Маршрут обязателен и должен содержать разделитель `=` между пунктами (переносы строк схлопываются в пробел); Год обязателен (1900–текущий); в диапазонах «Категория с/по» и «Месяц с/по» начальное значение не может быть позже конечного; файл — только `.zip` или `.pdf`.

### Редактирование опубликованного отчёта

Уже опубликованный отчёт можно отредактировать через ту же страницу `/upload.html`. Право на это имеют **администратор** и **пользователь, загрузивший отчёт** (определяется по полю `ЗагрузилID`).

- В форме загрузки введите Шифр-ДопШифр существующего отчёта. Когда код распознаётся как занятый и у вас есть право, рядом активируется кнопка-карандаш **«Редактировать отчёт»**.
- Нажатие подгружает данные опубликованного отчёта в форму (режим `edit_published`).
- Кнопка **«Опубликовать»** (для автора — «Сохранить») отправляет правку в `data.up/10_up` как новую заявку с маркером `.editmeta`. В таблице «на рассмотрении» она помечается бейджем **«ред.»** и проходит повторную модерацию администратором (как обычная заявка: Опубликовать / Отклонить).
- Администраторам приходит письмо «Отредактированный отчёт ... ожидает рассмотрения».
- Авторство отчёта (`ЗагрузилID`) при правке по умолчанию берётся из исходного отчёта. **Администратор** может переназначить загрузившего через блок «Загрузивший отчёт» прямо в форме (новый пользователь должен существовать в `auth.db`; очистка обнуляет `ЗагрузилID`). Кто фактически редактировал, фиксируется в маркере `.editmeta`.
- Данные формы подгружаются из `tlib.db`, а наличие/тип/размер файла определяются по фактическому файлу в `data/`. Если запись в БД и файл на диске расходятся (файл числится в БД, но отсутствует на диске; либо тип не совпадает), под полем файла в форме показывается предупреждение.
- Если у отчёта нет файла на диске и новый файл не приложен, правка сохраняется как **JSON-сирота** (без файла) — изменения уходят на рассмотрение, но автоматически опубликованы не будут, пока к заявке не приложат файл вручную.

### Удаление опубликованного отчёта

Удаление инициируется как **запрос** (автором или администратором) и подтверждается администратором:

1. В режиме редактирования опубликованного отчёта нажмите **«Удалить»**. В диалоге нужно ввести Шифр-ДопШифр отчёта (подтверждение намерения) и обязательно указать **причину удаления**.
2. Создаётся маркер `data.up/10_up/<ID>.delreq`, администраторам уходит письмо о запросе. В таблице «на рассмотрении» запрос отображается с бейджем **«удаление»**.
3. Администратор открывает запрос и:
   - **Подтвердить удаление** — создаётся триггер `data.up/20_go/<ID>.delete`, дальше File Watcher делает бэкап файлов в `data.old/` и пересобирает БД; инициатору уходит письмо об удалении;
   - **Отклонить запрос** — маркер `.delreq` удаляется, отчёт остаётся в библиотеке; инициатору уходит письмо об отклонении.
   - Чек-бокс **«Не отправлять письмо загрузившему»** под формой при установке подавляет письмо инициатору в обоих вариантах.

Подробности API и кодов ответов: [API: загрузка отчётов](details/API.md#загрузка-отчётов-apiupload).

### Загрузка нового отчета (вручную, копированием файлов)

**Требования к именам файлов:**
- С допшифром: `12345-а.json`, `12345-а.zip`, `12345-а.pdf`
- Без допшифра: `12345.json`, `12345.zip`, `12345.pdf`

**Шаги:**
```bash
# 1. Скопировать файлы в папку загрузки
cp 12345-а.json data.up/20_go/
cp 12345-а.zip data.up/20_go/
cp 12345-а.pdf data.up/20_go/

# 2. File Watcher обработает автоматически (каждые 60 сек)
#    После ~2-3 минут отчёт доступен на сайте.
#    Задержка — это stability-window: File Watcher ждёт, пока размер и mtime
#    файлов не замрут 3 скана подряд, чтобы не подхватить недозалитый архив.
```

**Что происходит:**
1. Stability-window: ждём, пока size+mtime файлов группы замрут 3 скана подряд
2. Файлы перемещаются в `data.up/30_processing/`
3. JSON проверяется на соответствие схеме
4. При успехе — копируются в `data/`, БД обновляется
5. При ошибке — перемещаются в `data.up/40_error/` с описанием

### Обновление существующего отчета

Процесс тот же. Поведение зависит от набора загружаемых файлов:

- **JSON + (PDF или ZIP)** — полная замена: все старые файлы отчёта (включая файлы с другим расширением) перемещаются в `data.old/` с timestamp, кэш архива инвалидируется. Например, если был `00123.zip`, а загружается `123.pdf` + `123.json`, старые `00123.zip` и `00123.json` уйдут в бэкап.
- **Только JSON** — обновление метаданных: в `data.old/` уходит только старый `.json`, PDF/ZIP и кэш не затрагиваются.
- **Только PDF или ZIP** — обновление архива: в `data.old/` уходит только файл с совпадающим расширением, JSON не затрагивается, кэш инвалидируется.

### Удаление отчета

```bash
# Создать пустой .delete файл
touch data.up/20_go/12345-а.delete

# File Watcher автоматически:
# 1. Удалит запись из БД
# 2. Переместит файлы в data.old/ (бэкап)
# 3. Обновит XLSX
```

### Обновление базы данных вручную

```bash
# Скопировать новую БД
cp new_database.db tlib-new.db

# Database Watcher автоматически (в течение 5 сек):
# 1. Создаст бэкап текущей БД
# 2. Заменит tlib.db
# 3. Обновит кэш
```

### Приостановка обработки

```bash
# Приостановить
mkdir data.up/pause

# Возобновить
rmdir data.up/pause

# Проверить статус
ls -d data.up/pause 2>/dev/null && echo "ПАУЗА" || echo "РАБОТАЕТ"
```

### Принудительная пересборка БД

Пересобирает `tlib.db` из всех JSON-файлов в `data/`. Применяется после ручной правки или восстановления файлов вне пайплайна.

```bash
touch data.up/20_go/reindex.now
# File Watcher пересоберёт БД в течение минуты
# (reindex.* обрабатывается без задержки stability-window)
```

Расширение файла не имеет значения (`reindex.txt`, `reindex.trigger` и т.д.). При успехе файл перемещается в `data.new/`, при ошибке — в `data.up/40_error/` с описанием.

## Мониторинг

### Панель администратора

Откройте `/admin` в браузере — дашборд с пятью панелями:

1. **Здоровье системы** — индикаторы: доступность БД, директории data, статус watchers, uptime
2. **Безопасность** — события из `critical.log` за последние 24 часа, топ IP по угрозам
3. **Состояние дисков** — директории `data*` сгруппированы по физическим дискам; объём, свободное место, % занятости
4. **Динамика пополнения** — количество отчётов, очередь загрузки, ошибки, добавлено за 24ч/7д/30д, последние добавленные
5. **Статистика посещений** — уникальных IP, запросов к поиску, просмотров отчётов, добавлений в кэш, загрузок файлов и API-запросов за 24ч/7д/30д; ошибки 4xx/5xx; топ отчётов по просмотрам (уник. IP) и топ скачиваний за 7 дней

Данные загружаются по кнопке «Обновить» (без автообновления).

#### Статистика посещений: детали

Статистика накапливается через `TrafficStatsMiddleware` на каждый запрос и сбрасывается в `data.secret/stats.db` каждые 5 минут. Данные хранятся 90 дней. В статистику не входят: JS/CSS/assets, `/favicon.ico` и внутренние запросы к `/data.db/`. Категории запросов:

| Категория | Пути |
|-----------|------|
| search    | `/api/search` |
| report    | `/?<шифр>` (просмотр страницы отчёта) |
| download  | `/data/*` (файлы отчётов) |
| api       | прочие `/api/*` |

**Доступ:** аутентификация через Magic Link (email). Страница доступна только пользователям с ролью `admin` или с email, совпадающим с `ROOT_ADMIN_EMAIL` из `data.secret/.env`. Неавторизованные видят только хедер с формой ввода email и общим статусом системы. В нижней части страницы — секция управления правами администраторов (выдача и отбор прав по email) и панель управления пользователями. См. [Безопасность](details/SECURITY.md).

### Управление пользователями через web-панель

Панель «7. Управление пользователями» на странице `/admin` (раздел `#admin-mgmt`) содержит три таблицы единой структуры:

| Столбец | Описание |
|---|---|
| Email | Адрес пользователя |
| Имя | Имя или «—» |
| IP | Последний IP входа (`last_login_ip`); «—» до первого входа |
| Последний вход | Дата и время последнего входа; «—» если не входил |

**Таблица 1 «Входившие»** — активные пользователи, входившие хотя бы раз; сортировка по дате последнего входа (сначала недавние).

**Таблица 2 «Без входов»** — активные пользователи, не входившие ни разу; сортировка по email; спрятана под кат (раскрывается кликом).

**Таблица 3 «Заблокированные»** — пользователи с `is_active=0`; сортировка по email.

Кнопки действий (неуместные — серые):
- **Заблокировать** — `is_active=0` + закрытие всех сессий. Серая для `ROOT_ADMIN_EMAIL` и собственной учётки (сервер также вернёт 403).
- **Разблокировать** — `is_active=1`. Доступна для всех заблокированных.
- **Выход** — завершает активные сессии пользователя. Для своей строки завершает все сессии, кроме текущей (чтобы не разлогиниться), и становится серой при единственной сессии. Для чужой строки — серая при отсутствии активных сессий.

Удаление пользователя доступно только через CLI (`tools/manage_users.py delete`).

Роль `admin` выдаётся/отбирается в панели «6. Управление правами администраторов».

### CLI-управление пользователями (break-glass)

Если web-интерфейс `/admin` недоступен, управляйте пользователями через утилиту `tools/manage_users.py` напрямую на сервере.

```bash
# Из корня проекта (/opt/TlibWebApp) с активированным venv:
source venv/bin/activate

# Список всех пользователей
python tools/manage_users.py list

# Активные сессии
python tools/manage_users.py sessions

# Заблокировать пользователя (и закрыть все сессии)
python tools/manage_users.py deactivate user@example.com

# Разблокировать
python tools/manage_users.py activate user@example.com

# Выдать роль admin
python tools/manage_users.py grant user@example.com admin

# Отобрать роль admin
python tools/manage_users.py revoke user@example.com admin

# Удалить пользователя и все его сессии
python tools/manage_users.py delete user@example.com
```

> Утилита напрямую читает и пишет `data.secret/auth.db`. `ROOT_ADMIN_EMAIL` из `.env` — постоянный суперадмин, его права через `revoke` не сбрасываются (логика в `app.state`/роутерах). Для Windows-консоли с кириллицей: `$env:PYTHONIOENCODING='utf-8'`.

### Быстрая диагностика

```bash
# Статус обработки файлов
ls data.up/20_go/*.json 2>/dev/null       # В очереди
ls data.up/30_processing/ 2>/dev/null     # В обработке
ls data.up/40_error/ 2>/dev/null          # С ошибками

# Последние события
tail -20 logs/app.log

# Критичные события за сегодня
grep "$(date +%Y-%m-%d)" logs/critical.log
```

### Мониторинг безопасности

```bash
# События безопасности
grep "category=SECURITY" logs/critical.log

# Атаки высокого уровня
grep "threat_level=\"HIGH\"" logs/critical.log

# Топ-10 IP по количеству событий
grep "category=SECURITY" logs/critical.log | grep -oP 'ip="\K[^"]*' | sort | uniq -c | sort -rn | head -10
```

### Что требует внимания

- `PATH_TRAVERSAL_ATTEMPT` — попытка взлома (HIGH)
- `RATE_LIMIT_EXCEEDED` — возможная DoS атака (MEDIUM)
- `CRITICAL` — критичные ошибки приложения

## Обслуживание

### Резервное копирование

**Что бэкапить:**
- `data/` — архивы отчетов
- `data.db/tlib.db` — база данных
- `data.secret/stats.db` — статистика посещений (опционально; пересоздаётся автоматически)

**Автоматические бэкапы:**
- `data.old/` — бэкапы файлов и БД при обновлении/удалении

### Очистка старых данных

```bash
# Удалить бэкапы старше 1 года
find data.old/ -type f -mtime +365 -delete

# Удалить старые бэкапы БД (оставить последние 10)
ls -t data.old/tlib_*.db | tail -n +11 | xargs rm -f

# Удалить stats.db (пересоздаётся автоматически при следующем запуске)
rm data.secret/stats.db
```

### Ротация логов

Логи ротируются автоматически:
- `app.log`: 20 МБ, хранится 5 файлов
- `debug.log`: 50 МБ, хранится 3 файла
- `critical.log`: 10 МБ, хранится 10 файлов

## Кеширование файлов

### Как работает кеширование

PDF отдаётся напрямую из `DATA_DIRECTORY`. При открытии отчёта клиент запускает подготовку кеша через Cache API:

1. `POST /api/cache/prepare/{archive_name}` — fire-and-forget запуск подготовки
2. Сервер извлекает файлы из архива, конвертирует изображения и PDF→PNG
3. `POST /api/cache/resolve/{archive_name}` — клиент проверяет готовность файлов

Готовые файлы хранятся в `data.cache/` с LRU-очисткой.

**Настройки** (`config/cache.py` и `config/media.py`):
- `MAX_CACHE_SIZE` — максимальный размер кеша (50 ГБ по умолчанию)
- `PDF_TO_PNG_ENABLED` — конвертация PDF в PNG страницы (требует PyMuPDF)
- `IMAGE_TO_JPG_ENABLED` — оптимизация изображений при извлечении

### Мониторинг кеша

```bash
# Размер кеша
du -sh data.cache/

# Количество файлов
ls data.cache/ | wc -l

# Типы файлов в кеше
ls data.cache/*.pdf 2>/dev/null | wc -l  # PDF
ls data.cache/*-geo_*.zip 2>/dev/null | wc -l  # GPS архивы

# Самые большие файлы в кеше
ls -lhS data.cache/ | head -20
```

### Очистка кеша

```bash
# Полная очистка (безопасно, файлы пересоздадутся при запросе)
rm -rf data.cache/*

# Удалить только standalone PDF (отдельные, не из архивов)
# Формат: {filename}_{HASH}.pdf (одно подчёркивание перед хешем)
find data.cache/ -name '*_[A-F0-9][A-F0-9][A-F0-9][A-F0-9][A-F0-9][A-F0-9][A-F0-9][A-F0-9].pdf' -delete

# Удалить файлы старше 30 дней (не используются)
find data.cache/ -type f -mtime +30 -delete
```

**Примечание:** LRU-очистка происходит автоматически при превышении `MAX_CACHE_SIZE`. Файлы с самым старым временем последнего использования (mtime) удаляются первыми.

При обновлении отчёта через File Watcher (загрузка ZIP или PDF в `data.up/20_go/`) кеш для этого архива **автоматически инвалидируется** — ручная очистка не нужна. При загрузке только JSON без архива кеш не затрагивается.

## Восстановление

### Откат базы данных

```bash
# Посмотреть доступные бэкапы
ls -la data.old/tlib_*.db

# Восстановить нужный бэкап
cp data.old/tlib_20251205_093000.db tlib-new.db
# Database Watcher применит автоматически
```

### Восстановление удаленного отчета

```bash
# 1. Найти файлы в бэкапе
ls data.old/ | grep 12345

# 2. Скопировать обратно (убрать timestamp из имени)
mv data.old/12345-а_20251225_090049.json data/12345-а.json
mv data.old/12345-а_20251225_090049.pdf data/12345-а.pdf
mv data.old/12345-а_20251225_090049.zip data/12345-а.zip

# 3. Восстановить запись в БД
cp data/12345-а.json data.up/20_go/
# File Watcher добавит запись обратно
```

### Обработка ошибок загрузки

```bash
# 1. Посмотреть описание ошибки
cat data.up/40_error/12345-а.err

# 2. Исправить JSON файл

# 3. Переместить обратно в очередь
mv data.up/40_error/12345-а.* data.up/20_go/
```

#### Особый случай: «ТипФайла=zip, но архив для карточки отсутствует»

Если в `40_error/` лежит JSON с этой ошибкой, а в `data.up/20_go/` при этом уже лежит соответствующий ZIP/PDF — это симптом старого бага (до обновления File Watcher). Архив доехал позже JSON и был проигнорирован.

Восстановление:
```bash
# Вернуть JSON в очередь (ZIP уже там)
mv data.up/40_error/12345-а.json data.up/20_go/
rm data.up/40_error/12345-а.err

# File Watcher подхватит оба файла как полную группу (complete) в следующем цикле
```

После обновления File Watcher этот сценарий исключён: JSON с `ТипФайла=zip/pdf` остаётся в `20_go/` и ждёт архив, не уходя в `40_error/`.
