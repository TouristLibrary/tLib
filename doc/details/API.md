## POST /api/search

Поиск отчетов в базе данных.

### Параметры (form-data)

| Параметр | Тип | Описание |
|----------|-----|----------|
| Шифр | string | Шифр (точное совпадение) |
| ДопШифр | string | ДопШифр |
| Маршрут | string | Поиск в маршруте (по словам) |
| РайонОбщий | string | Общий район |
| Район | string | Конкретный район |
| Автор | string | Автор (по словам) |
| Тип | string | Тип похода |
| КатегорияС | string | Категория начальная |
| КатегорияПо | string | Категория итоговая |
| ГодС | string | Год начала диапазона |
| ГодПо | string | Год конца диапазона |
| МесяцС | string | Месяц начала (1-12) |
| МесяцПо | string | Месяц конца (1-12) |
| ЗагруженоС | string | Дата загрузки с (YYYY-MM-DD) |
| sortColumn | string | Столбец сортировки: `Год` (default), `Категория`, `ДатаВремяЗагрузки` |
| sortOrder | string | Направление: `desc` (default, от больших к меньшим), `asc` |
| limit | integer | Размер страницы для пагинации |
| offset | integer | Смещение для пагинации |

### Ответ

```json
[
  {
    "Шифр": 12345,
    "ДопШифр": "а",
    "Маршрут": "По Байкалу",
    "РайонОбщий": "Восточная Сибирь",
    "Район": "Байкал",
    "Автор": "Иванов И.И.",
    "Город": "Иркутск",
    "Тип": "водный",
    "ТипСудна": "байдарка",
    "КатегорияС": "2",
    "КатегорияПо": "2Б",
    "Год": 2024,
    "МесяцС": 7,
    "МесяцПо": 8,
    "Комментарии": "",
    "РазмерАрхива": 15728640,
    "ТипФайла": "zip"
  }
]
```

Если у отчёта есть запись в [списке скрытых отчётов](#get-apiadminhidden-reports), в строке присутствует поле `"Скрыт": true` (иначе поле отсутствует). Отчёт участвует в поиске как обычно; фронтенд по этому флагу гасит ссылку/иконку скачивания и на странице отчёта показывает только карточку.

### Пример

```bash
curl -X POST http://localhost:8080/api/search \
  -d "god=2024" \
  -d "tip=водный"
```

## GET /api/pdf/{id}

Просмотр PDF файла.

### Параметры

- `id` — имя PDF файла (например, `12345-а.pdf`)

### Поведение

PDF отдаётся напрямую из `DATA_DIRECTORY`. Конвертация PDF в PNG страницы для встроенного вьюера выполняется отдельно через Cache API (`/api/cache/prepare`, `/api/cache/resolve`).

### Заголовки ответа

- `Content-Disposition: inline` — PDF открывается в браузере
- `ETag` — идентификатор версии файла
- `Last-Modified` — время изменения файла
- `Cache-Control: must-revalidate` — браузер должен проверять актуальность

### Условные запросы

Поддерживает заголовки:
- `If-None-Match` — проверка ETag
- `If-Modified-Since` — проверка времени изменения

При совпадении возвращает `304 Not Modified` без тела.

### Пример

```bash
# Открыть PDF в браузере
curl http://localhost:8080/api/pdf/12345-а.pdf

# С условным запросом (ETag)
curl -H 'If-None-Match: W/"pdf:123456789-1048576"' http://localhost:8080/api/pdf/12345-а.pdf
# Ответ: 304 Not Modified (если файл не изменился)
```

## Авторизация (/api/auth/*)

Беспарольный вход через magic link + 6-значный цифровой код. При запросе ссылки на email отправляется письмо с двумя способами войти: кликнуть ссылку (то же устройство) или ввести код (любое устройство).

**Хранение:** отдельная SQLite `auth.db`. Токены и коды — только SHA-256 хеши, raw-значения в БД не попадают.

### POST /api/auth/request-link

Запросить magic link и цифровой код.

**Тело (JSON):** `email` (обязателен), `name` (опционально, устанавливается только при первом создании пользователя), `redirect` (опционально, путь для редиректа после входа по ссылке; должен начинаться с `/` и не содержать `//`).

**Порядок проверок / лимиты:**
1. Пер-IP троттлинг: не более 5 запросов за 10 мин с одного IP (in-memory).
2. Пер-email: 1 запрос в 60 с на email (`AUTH_MAGIC_LINK_RATE`). При повторном запросе предыдущий код аннулируется.
3. Дневной лимит: не более 400 писем в сутки UTC (`AUTH_EMAIL_DAILY_CAP`, персистентно в `auth.db`). При исчерпании — WARNING в логи + `EMAIL_QUOTA` алерт администратору.

**Ответ при успехе:**
```json
{"ok": true}
```

**Ответ 429 (структурированный):**
```json
{"error": "<RU-текст с таймингом>", "reason": "ip_throttle|email_rate|daily_cap", "retry_after": <сек>}
```
Текст не раскрывает существование email. Все три UI входа (`login.html`, `admin.html`, `upload.html`) показывают `error` пользователю.

**Ошибки:** 400 (некорректный email / JSON), 403 (пользователь заблокирован), 429 (лимиты), 500 (SMTP недоступен).

---

### GET /auth/verify

Обрабатывает клик по ссылке из письма. Параметры query: `token` (обязателен), `redirect` (опционально).

При успехе — устанавливает cookie `session_token` (httponly, samesite=strict) и делает `302` редирект на `redirect` (или `/login.html`).

При ошибке (токен не найден, истёк, пользователь заблокирован) — редирект на `{redirect}?error=expired`.

---

### POST /api/auth/verify-code

Проверить 6-значный цифровой код. Создаёт сессию на устройстве, где введён код.

**Тело (JSON):** `email` (обязателен), `code` (обязателен, 6 цифр).

**Лимит попыток:** 5 неверных попыток аннулируют код.

**Ответ при успехе:**
```json
{"ok": true}
```
Cookie `session_token` устанавливается (те же параметры, что при `/auth/verify`).

**Ошибки:** 400 (некорректный запрос), 401 (неверный или устаревший код), 403 (пользователь заблокирован).

---

### POST /api/auth/logout

Удаляет сессию из БД и очищает cookie.

**Параметр query:** `?all=1` — удаляет **все** сессии пользователя (выход со всех устройств). Без параметра — удаляет только текущую сессию.

**Ответ:** `{"ok": true}`

UI: на страницах `login.html`, `admin.html`, `upload.html` кнопка «Выйти» открывает dropdown с пунктами «Выйти» и «Выйти со всех устройств».

---

### GET /api/auth/me

Возвращает данные текущего пользователя по cookie. Для администраторов дополнительно проверяется, что запрос пришёл из той же подсети (/24 IPv4, /64 IPv6), что и при создании сессии.

**Ответ:**
```json
{"id": 1, "email": "user@example.com", "name": "Имя", "role": ""}
```

**Ошибки:** 401 (нет cookie или сессия истекла/невалидна).

## Загрузка отчётов (/api/upload/*)

Загрузка отчётов пользователями с модерацией администраторами. Аутентификация — Magic Link (cookie `session_token`, общая система `services/auth/`). Загруженный отчёт попадает в staging `data.up/10_up`, откуда админ публикует его в `data.up/20_go` (далее обрабатывает File Watcher) или отклоняет.

Помимо загрузки новых отчётов, поддерживаются **правка и удаление уже опубликованных** отчётов. Право на правку/удаление имеют администраторы и пользователь, который загрузил отчёт (по полю `ЗагрузилID`). Попытка без прав возвращает `403 Forbidden`.

Нормализация ID: Шифр → 5 цифр с ведущими нулями, ДопШифр → UPPERCASE (например, `1` + `tlib` → `00001-TLIB`).

### GET /api/upload/next-code

Первый свободный номер `N` для дефолтного кода `N-TLIB` среди всех источников (`tlib.db`, `10_up`, `20_go`, `30_processing`). Перебор начинается со 101. Требует авторизацию (401 без сессии).

```json
{"shifr": 142, "dopshifr": "TLIB"}
```

### GET /api/upload/check-code

Проверка уникальности Шифр-ДопШифр (для live-подсветки в форме). Требует авторизацию.

**Параметры (query):** `shifr` (int, обязателен), `dopshifr` (string, по умолчанию пусто), `exclude` (нормализованный ID, исключаемый из проверки — для режима редактирования).

```json
{"taken": true, "normalized": "00042-TLIB", "in_library": true, "can_edit": true, "zagruzil_id": 7}
```

| Поле | Описание |
|------|----------|
| `taken` | Код уже занят (в `tlib.db`, `10_up`, `20_go` или `30_processing`) |
| `normalized` | Нормализованный ID |
| `in_library` | Код принадлежит **опубликованному** отчёту (есть в `data/` или `tlib.db`) |
| `can_edit` | Текущий пользователь вправе редактировать занятый опубликованный отчёт (админ или автор по `ЗагрузилID`) — драйвер кнопки «Редактировать отчёт» |
| `zagruzil_id` | `ЗагрузилID` опубликованного отчёта (или `null`) |

### POST /api/upload/submit

Сохраняет отчёт (`multipart/form-data`) в `data.up/10_up` и уведомляет админов письмом. Требует авторизацию.

**Поля формы:** `shifr` (int, обязателен), `god` (int, обязателен), `marshrut` (обязателен), `file` (zip/pdf, обязателен), `dopshifr` (по умолчанию `TLIB`), `raion_obshiy`, `raion`, `avtor`, `tip`, `kategoriya_s`, `kategoriya_po`, `mesyats_s`, `mesyats_po`, `tip_sudna`, `gorod`, `kommentarii`, `zagruzil_imya`.

**Только для администраторов (необязательные):** `uploader_id` (int) — переназначить `ЗагрузилID` на указанного пользователя (проверяется по `auth.db`); `uploader_cleared` (bool) — обнулить `ЗагрузилID`. Если пользователь с `uploader_id` не найден в `auth.db`, значение игнорируется.

Бэкенд проставляет автоматически: `РазмерАрхива`, `ТипФайла`, `КоличествоСтраниц` (для PDF через PyMuPDF), `ЗагрузилID` (из сессии, может быть переопределён администратором), `ДатаВремяЗагрузки`. `ЗагрузилИмя` берётся из формы как есть. Поле `ИмяФайла` удалено — имя файла выводится из ID и `ТипФайла`.

```json
{"ok": true, "id": "00042-TLIB"}
```

**Коды ответов:** `200` — успех; `400` — недопустимое расширение или ДопШифр; `409` — Шифр-ДопШифр уже занят (`{"code_taken": true}`); `413` — файл больше `MAX_ARCHIVE_SIZE` (проверяется при потоковой записи); `507` — недостаточно места на диске; `401` — не авторизован.

**Механизм приёма файла:** файл пишется чанками (1 МБ) во временный файл в `data.up/10_up/`. При превышении лимита — temp удаляется, возвращается 413. После успешного стрима — атомарный rename в финальное имя. RAM на запрос — ≈ 1 МБ.

### GET /api/upload/status

Возвращает текущее состояние подсистемы загрузки. Требует авторизацию. Используется фронтендом при открытии страницы.

```json
{"uploads_enabled": true, "reason": null, "free_gb": 45.3, "used_pct": 55}
{"uploads_enabled": false, "reason": "disk_critical", "free_gb": 3.1, "used_pct": 91}
```

| Поле | Описание |
|------|----------|
| `uploads_enabled` | `true` — загрузки разрешены; `false` — блокированы |
| `reason` | `null`, `"disk_critical"` (≥ 90% занято) или `"disk_reserve"` (< 4 ГБ свободно) |
| `free_gb` | Свободное место на томе `data.up/10_up/` в ГБ; `null` если метрики диска временно недоступны |
| `used_pct` | Занятость тома в %; `null` если метрики диска временно недоступны |

**Коды:** `200` — всегда; `401` — не авторизован.

### GET /api/upload/lookup-user

Резолв пользователя `auth.db` по `id` или `email`. Только админ.

**Параметры (query, один из двух):** `id` (int) — поиск по первичному ключу; `email` (string) — поиск по e-mail.

```json
{"found": true, "id": 7, "email": "user@example.com", "name": "Петров"}
{"found": false}
```

**Коды:** `200` — всегда (поле `found` указывает на результат); `401` — не администратор.

### GET /api/upload/list

Список заявок на рассмотрении в `data.up/10_up`. Только админ (401 без админ-сессии). В список входят как обычные отчёты, так и правки опубликованных и запросы на удаление.

```json
{
  "ok": true,
  "reports": [
    {
      "id": "00042-TLIB", "type": "report", "shifr": 42, "dopshifr": "TLIB",
      "marshrut": "По Байкалу", "autor": "Иванов И.И.", "god": 2025,
      "zagruzil": "Петров", "data_zagruzki": "2026-06-01T10:00:00+00:00",
      "tip_faila": "pdf", "razmer": 5242880, "has_archive": true,
      "zagruzil_id": 7, "is_edit": false
    },
    {
      "id": "00031-TLIB", "type": "delete_request", "shifr": 31, "dopshifr": "TLIB",
```

### GET /api/upload/item

JSON одного отчёта из `10_up` для редактирования. Только админ.

**Параметры (query):** `id` — нормализованный ID.

```json
{"ok": true, "data": { "Шифр": 42, "ДопШифр": "TLIB", "...": "..." }, "has_archive": true, "archive_ext": "pdf", "uploader_id": 7, "uploader_name": "Петров", "uploader_email": "petrov@example.com", "orig_id": "00042-OLD"}
```

`orig_id` — ID исходного опубликованного отчёта (при правке со сменой шифра); `null`, если шифр не менялся. Используется в UI для предупреждения о замене.

**Коды:** `200` — успех; `404` — отчёт не найден; `401` — не админ.

### GET /api/upload/file

Скачивание файла архива отчёта как вложения (`Content-Disposition: attachment`). Только админ. Файл ищется в `10_up`, а если там его нет (json-only правка, у которой архив остался в библиотеке) — в `data/`.

**Параметры (query):** `id` — нормализованный ID. MIME из `MIME_TYPES` по расширению, иначе `application/octet-stream`.

**Коды:** `200` — файл; `404` — файл не найден; `401` — не админ.

### POST /api/upload/publish

Сохраняет правки администратора и переносит пару json+файл из `10_up` в `20_go` (далее — обычный pipeline File Watcher). Принимает `multipart/form-data`. Только админ.

**Поля:** `id` (обязателен), `admin_comment`, все поля отчёта (как в `submit`), `remove_file` (bool), `no_email` (bool, по умолчанию false), `file` (необязателен — если не передан, используется существующий архив из `10_up`), `uploader_id` (int, необязателен — переназначить `ЗагрузилID`), `uploader_cleared` (bool — обнулить `ЗагрузилID`).

**Авто-удаление при смене шифра:** если рядом с заявкой есть `<ID>.editmeta` и зафиксированный в нём `orig_id` отличается от итогового кода, в `20_go` автоматически создаётся `.delete`-триггер для `orig_id` — File Watcher переместит старые файлы в `data.old/` и исключит старую запись из БД. Маркер `.editmeta` удаляется из `10_up` независимо от смены кода.

Письмо загрузившему **отложено**: создаётся маркер `data.up/<ID>.notify`, и письмо отправляет File Watcher после реальной публикации отчёта в `data/`. Если `no_email: true`, маркер не создаётся и письмо не отправляется.

```json
{"ok": true, "id": "00042-TLIB"}
```

**Коды:** `200` — успех; `400` — нет id / нет файла для публикации; `404` — отчёт не найден в очереди; `409` — Шифр-ДопШифр занят; `413` — файл слишком большой; `401` — не админ.

### POST /api/upload/reject

Перемещает отчёт из `10_up` в `data.old/` с timestamp, создаёт `<ID>_<ts>.err` с комментарием и **сразу** отправляет письмо загрузившему. Тело — JSON. Только админ.

**Тело (JSON):** `{"id": "00042-TLIB", "admin_comment": "Причина отклонения", "no_email": false}`. При `no_email: true` письмо загрузившему не отправляется; перенос в `data.old/` и `.err` выполняются как обычно. Если рядом есть `<ID>.editmeta`, он переносится в `data.old/` вместе с парой (`<ID>_<ts>.editmeta`).

```json
{"ok": true}
```

**Коды:** `200` — успех; `400` — нет id / невалидный JSON; `404` — отчёт не найден; `401` — не админ.

### GET /api/upload/published-item

Данные **опубликованного** отчёта из `tlib.db` для режима редактирования (карточка собирается через `build_dict_from_row`, автор дополняется из `auth.db` по `ЗагрузилID`). Диск `data/` сканируется только для детекции фактического наличия/типа/размера архива. Доступен автору отчёта (`ЗагрузилID`) и администраторам.

**Параметры (query):** `id` — нормализованный ID.

```json
{
  "ok": true,
  "data": { "Шифр": 42, "ДопШифр": "TLIB", "...": "..." },
  "has_archive": true,
  "archive_ext": "pdf",
  "file_status": { "mismatch": null, "message": null },
  "uploader_id": 7,
  "uploader_name": "Петров",
  "uploader_email": "petrov@example.com",
  "pending_delete": false,
  "delete_reason": null,
  "delete_requested_by_email": null,
  "delete_requested_at": null
}
```

`has_archive`, `archive_ext`, а также `РазмерАрхива`/`ТипФайла` внутри `data` берутся с диска, если файл фактически есть в `data/`; иначе — из `tlib.db`.

`file_status` отражает расхождение между записью в `tlib.db` и файлом на диске (для предупреждения в форме):

| `mismatch` | Условие |
|------------|---------|
| `null` | Файл есть и в БД, и на диске, типы совпадают — расхождения нет |
| `none` | Файла нет ни в БД, ни на диске |
| `db_only` | В БД отчёт числится с файлом, но на диске файла нет |
| `disk_only` | В БД файл не указан, но на диске файл есть |
| `type_mismatch` | Тип файла в БД и на диске различается (например, `zip` vs `pdf`) |

Если на отчёт уже есть запрос на удаление (`.delreq` в `10_up`), то `pending_delete: true` и заполняются `delete_reason`, `delete_requested_by_email`, `delete_requested_at`.

**Коды:** `200` — успех; `404` — отчёт не найден в библиотеке; `403` — нет прав на редактирование; `401` — не авторизован.

### POST /api/upload/submit-edit

Сохраняет правку опубликованного отчёта в `data.up/10_up` (json + файл) вместе с сайдкар-маркером `<ID>.editmeta`. Новая версия уходит на модерацию так же, как новый отчёт (в `/api/upload/list` помечается `is_edit: true`). Принимает `multipart/form-data`. Доступен автору отчёта и администраторам.

**Поля:** `edit_orig_id` (обязателен — ID редактируемого отчёта), все поля отчёта (как в `submit`), `remove_file` (bool), `file` (необязателен — если не передан, метаданные и сам архив берутся с диска `data/`), `uploader_id` (int, только для администратора — переназначить `ЗагрузилID`), `uploader_cleared` (bool, только для администратора — обнулить `ЗагрузилID`).

**Поведение без нового файла:**
- если архив отчёта есть на диске (`data/`), он копируется в `10_up` вместе с JSON;
- если архива на диске **нет** (отчёт числится в БД, но файл отсутствует), правка сохраняется как **JSON-сирота** — без файла. Ответ содержит `orphan: true` и `warning`. Такая заявка уходит на модерацию, но автоматически опубликована не будет, пока к ней не приложат файл.

**Авторство:** По умолчанию `ЗагрузилID` берётся из исходного опубликованного отчёта и не изменяется при правке автором. **Администратор** может переназначить загрузившего через поля `uploader_id` (перезаписать `ЗагрузилID` другим пользователем из `auth.db`) или `uploader_cleared` (обнулить `ЗагрузилID`; `ЗагрузилИмя` при этом не трогается). Если `uploader_id` не найден в `auth.db`, значение игнорируется. Кто фактически правил отчёт, фиксируется отдельно в сайдкар-маркере `.editmeta` (поля `edited_by_id`, `edited_by_email`, `edited_at`).

```json
{"ok": true, "id": "00042-TLIB"}
```

Вариант с JSON-сиротой (файла нет ни в новой загрузке, ни на диске):

```json
{"ok": true, "id": "00042-TLIB", "orphan": true, "warning": "Изменения сохранены, но файл отчёта на диске не найден. JSON-сирота отправлен на рассмотрение, однако автоматически опубликован не будет — для публикации необходимо прикрепить файл."}
```

Администраторам уходит письмо «Отредактированный отчёт ... ожидает рассмотрения» (`send_new_report_notice(is_edit=True)`).

**Коды:** `200` — успех (включая JSON-сироту с `orphan: true`); `400` — недопустимое расширение / ДопШифр; `403` — нет прав; `409` — Шифр-ДопШифр занят (`{"code_taken": true}`); `413` — файл слишком большой; `401` — не авторизован. `{"no_file": true}` возвращается только при `remove_file=true` без нового файла, когда удалять нечего.

### POST /api/upload/request-delete

Создаёт запрос на удаление опубликованного отчёта — маркер `<ID>.delreq` в `10_up`. Требует подтверждения намерения вводом Шифр-ДопШифр. Доступен автору отчёта и администраторам. Тело — JSON.

**Тело (JSON):** `{"id": "00042-TLIB", "confirm_code": "42-TLIB", "reason": "Причина удаления"}`. Код подтверждения сравнивается с ID нестрого (без пробелов, регистра и ведущих нулей).

```json
{"ok": true}
```

Администраторам уходит письмо о запросе удаления (`send_delete_request_notice`).

**Коды:** `200` — успех; `400` — нет id/confirm_code/reason или невалидный JSON; `409` — введённый код не совпадает (`{"code_mismatch": true}`); `403` — нет прав; `404` — отчёт не найден в библиотеке; `401` — не авторизован.

### POST /api/upload/confirm-delete

Подтверждает удаление: создаёт `.delete`-триггер `<ID>.delete` в `data.up/20_go` (дальше File Watcher делает бэкап в `data.old/` и пересобирает БД) и удаляет маркер `.delreq`. Только админ. Тело — JSON.

**Тело (JSON):** `{"id": "00042-TLIB", "admin_comment": "Необязательный комментарий", "no_email": false}`. При `no_email: true` письмо инициатору не отправляется; триггер `.delete` создаётся как обычно.

```json

```

Инициатору запроса уходит письмо об удалении (`send_delete_decision(confirmed=True)`).

**Коды:** `200` — успех; `400` — нет id / невалидный JSON; `401` — не админ.

### POST /api/upload/reject-delete

Отклоняет запрос на удаление: удаляет маркер `<ID>.delreq` из `10_up`. Отчёт остаётся в библиотеке. Только админ. Тело — JSON.

**Тело (JSON):** `{"id": "00042-TLIB", "admin_comment": "Необязательный комментарий", "no_email": false}`. При `no_email: true` письмо инициатору не отправляется; маркер `.delreq` удаляется как обычно.

```json
{"ok": true}
```

Инициатору запроса уходит письмо об отклонении (`send_delete_decision(confirmed=False)`).

**Коды:** `200` — успех; `400` — нет id / невалидный JSON; `404` — запрос на удаление не найден; `401` — не админ.

## GET /admin

Панель администратора — HTML-страница с дашбордом состояния системы.

### Доступ

Страница отдаётся всем (200). Содержимое зависит от аутентификации:
- **Не авторизован** — хедер с формой ввода email (Magic Link), кнопкой «Обновить» и индикатором общего состояния
- **Авторизован, но не админ** — хедер с email и сообщением «Нет прав администратора»
- **Авторизован как админ** (`role='admin'` или `ROOT_ADMIN_EMAIL`) — все панели + секция управления правами

Аутентификация через cookie `session_token` (Magic Link, общая система `services/auth/`).

### Панели дашборда

1. **Здоровье системы** — индикаторы: БД, директория data, watchers, uptime
2. **Безопасность** — события из `critical.log` за последние 24 часа
3. **Состояние дисков** — группировка `data*` директорий по физическим дискам, объём и % занятости
4. **Динамика пополнения** — количество отчётов, очередь, ошибки, добавлено за 24ч/7д/30д
5. **Статистика посещений** — уникальные IP, поиск, просмотры отчётов, кэш, загрузки, API; ошибки; топ отчётов и скачиваний за 7 дней
6. **Управление правами** — выдача прав по email, отбор прав у отмеченных админов (кроме `ROOT_ADMIN_EMAIL`)

## POST /api/admin/hidden-reports

Сохраняет список скрытых отчётов. Только для авторизованных админов.

Скрытый отчёт остаётся в результатах `/api/search` как обычно (см. поле `Скрыт` там), но:
- `/api/cache/{id}/prepare`, `/api/cache/{id}/resolve` и `/api/cache/{id}/contents` отвечают так, как если бы файл отсутствовал (кеш не готовится);
- на странице отчёта фронтенд показывает только карточку с плашкой «Отчет временно недоступен» (ссылка/иконка скачивания отключены).

Список хранится как одна настройка (`hidden_reports`) в `auth.db` (`app_settings`) — `tlib.db` доступна API только на чтение. Кэш в памяти — `app.state.hidden_reports`, обновляется сразу при сохранении.

### Запрос

```json
{"text": "00012-TLIB; 345, 00099-FRT"}
```

Токены разбираются по разделителям `;`, `,`, пробел/перенос строки; каждый нормализуется (Шифр → 5 цифр, ДопШифр → UPPERCASE), как везде в подсистеме загрузки. Пустой текст допустим — означает «скрытых отчётов нет».

### Ответ (200)

```json
{"ok": true, "text": "00012-TLIB\n00099-FRT\n00345"}
```

### Коды ответов

| Код | Условие |
|-----|---------|
| 200 | Успех |
| 400 | Невалидный JSON или один из токенов не распознан (ответ содержит `error` с перечислением) |
| 401 | Не авторизован или не админ |

## GET /robots.txt

Файл robots.txt с правилами индексации для поисковых краулеров.
Генерируется динамически (для подстановки актуального `SITE_URL` в Sitemap).

### Ответ

```
User-agent: *
Disallow: /data/
Disallow: /data.db/
Disallow: /api/
Disallow: /health

Sitemap: https://tlib.ru/sitemap.xml
```

| Путь | Правило |
|------|---------|
| `/data/` | Disallow — PDF/ZIP не индексируются (посадочная — карточка отчёта) |
| `/data.db/` | Disallow — каталог и БД не индексируются |
| `/api/` | Disallow |
| `/health` | Disallow |
| Остальное | разрешено по умолчанию |

Служебные страницы (`/oldscan.html`, `/cloud.html`, `/png-viewer`, `/login.html`, `/upload.html`)
закрыты через `X-Robots-Tag: noindex` в ответе, а не через `Disallow` —
чтобы краулер мог прочитать сам заголовок.

## GET /sitemap.xml

Динамический XML-сайтмап всех индексируемых страниц.

### Логика генерации

- Статические URL: `/`, `/about.html`.
- По одному URL для каждого отчёта в формате `/?{Шифр}[-{ДопШифр}]` (каноническая форма из `build_canonical_query`).
- Кириллический ДопШифр URL-кодируется (`urllib.parse.quote`); URL XML-экранируется.
- Формат: XML с namespace `http://www.sitemaps.org/schemas/sitemap/0.9`, без `<lastmod>`.

### Кеш

Результат кешируется в памяти. Инвалидация по `app.state.reference_version`:
при обновлении БД через watcher `reference_version` меняется и кеш сбрасывается.

### Объём

~12 000 URL + 2 статических. Лимит sitemap (50 000 URL) не достигается.

## GET / (SEO-поведение)

Корневой маршрут, обрабатываемый `static_router.py::root()`:

| Запрос | Ответ |
|--------|-------|
| `GET /` (без query) | Кешированный шаблон `index.html` (главная) |
| `GET /?123`, `GET /?123-ТССР` и отчёт найден | `index.html` с per-report `<title>`, `<meta description>`, `<link rel="canonical">` и видимым блоком маршрута вместо спиннера |
| `GET /?123` и отчёт **не найден** | Шаблон главной + `X-Robots-Tag: noindex, nofollow` (soft-404, статус 200) |
| `GET /?Шифр=...&Тип=...` (фильтры) | Шаблон главной + `X-Robots-Tag: noindex, nofollow` |
| `GET /?id=...` (legacy) | `RedirectResponse` по таблице редиректов |

Видимый блок маршрута зеркалит разметку JS-карточки (`renderSingleResultFormatted`):
доступен сразу в HTML — для краулеров (Яндекс, Google) и для пользователей до отрисовки JS.
JS перезаписывает `#results` как обычно, поведение не меняется.

## POST /api/cache/{archive_name}/prepare

Запуск подготовки кеша (fire-and-forget). Извлекает файлы из архива, конвертирует изображения и PDF→PNG.

### Параметры

- `archive_name` — идентификатор архива (например, `12345-а`)

### Ответ

```json
{"status": "started"}
```

### Статусы ответа

| Статус | Описание |
|--------|----------|
| ready | Кеш уже подготовлен |
| started | Подготовка запущена |
| already_preparing | Подготовка уже идёт |
| not_found | Архив не найден |

## GET /api/cache/{archive_name}/contents

Список файлов из кеша (`_meta.json`). Формат ответа совместим с `/api/archive/.../contents` и используется фронтендом когда физическое хранилище недоступно.

### Параметры пути

- `archive_name` — идентификатор архива (например, `12345-а`)

### Ответ

```json
{
  "name": "12345-а",
  "files": [
    {
      "name": "1-TST/Отчет.pdf",
      "size": 1048576,
      "compressed_size": 1048576,
      "download_url": "/cache/12345-а/1-TST/%D0%9E%D1%82%D1%87%D0%B5%D1%82.pdf"
    },
    {
      "name": "1-TST/tracks/route.gpx",
      "size": 15360,
      "compressed_size": 15360,
      "download_url": "/cache/12345-а/1-TST/tracks/route.gpx"
    }
  ],
  "download_url": "/data/12345-а.zip"
}
```

`download_url` файлов указывает на `/cache/` (StaticFiles) — файлы отдаются напрямую из `data.cache/` без обращения к физическому ZIP.

### Коды ответов

- `200` — кеш найден и валиден
- `202` — кеш готовится (фронтенд повторяет запрос с backoff)
- `404` — кеш не найден или устарел

### Ответ 202 (кеш готовится)

```json
{
  "status": "preparing",
  "stage": "converting",
  "detail": "",
  "retry_after": 1000
}
```

## POST /api/cache/{archive_name}/resolve

Resolve статуса кешированного файла. Клиент опрашивает этот endpoint для получения URL готового файла.

### Параметры

- `archive_name` — идентификатор архива

### Тело запроса (JSON)

```json
{
  "path": "document.pdf",
  "kind": "pdf"
}
```

| Поле | Значения | Описание |
|------|----------|----------|
| path | string | Путь к файлу внутри архива (пустой для all_tracks) |
| kind | pdf, image, track, all_tracks | Тип запрашиваемого файла |

### Ответы

**Файл готов (PDF):**
```json
{"status": "ready", "png_dir": "12345-а/report-png_A7F3B2E1", "pages": 15}
```

**Файл готов (image):**
```json
{"status": "ready", "url": "/cache/12345-а/1-TST/photo.jpg"}
```

**Файл готов (track):**
```json
{"status": "ready", "url": "/cache/12345-а/1-TST/route.gpx"}
```

**Файл готов (all_tracks):**
```json
{"status": "ready", "url": "/cache/12345-а/12345-а-geo.zip"}
```

**Подготовка в процессе:**
```json
{"status": "preparing", "stage": "extracting", "detail": "", "retry_after": 1000}
```

**Ошибка:**
```json
{"status": "error", "message": "..."}
```
