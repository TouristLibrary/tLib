# File Watcher

Автоматическая система обработки загружаемых файлов через staged pipeline.

---

## Pipeline

```
data.up/10_up/              → Модерация: сюда пишет страница /upload.html (pipeline не трогает)
  ↓ (admin publish на /upload.html → 20_go; reject → data.old + .err)
data.up/20_go/              → Точка входа pipeline
  ↓
  ├─ .json/.zip/.pdf       → Загрузка/обновление отчетов
  ├─ .delete               → Удаление отчетов
  └─ reindex.*             → Принудительная пересборка БД (любое расширение)
  ↓ Stability-window       → Ждём, пока size+mtime не замрут N сканов
                             (защита от недозалитых файлов)
data.up/30_processing/      → Валидация
  ↓ Проверка кодировки     → Null bytes, суррогаты
  ↓ Проверка JSON          → Валидация по схеме
  ↓ Финальная проверка     → БД из всех файлов
  ↓
data/                       → Атомарное копирование
  ↓
tlib-new.db                → Публикация БД (корень проекта)
  ↓
data.new/                  → Успех
или
data.up/40_error/          → Ошибка (+ .err файл)
```

---

## Staging 10_up и веб-загрузка

`data.up/10_up/` — staging-зона модерации. Pipeline File Watcher её **не сканирует**: файлы туда кладёт страница загрузки `/upload.html` (`POST /api/upload/submit`), а разбирает их администратор на той же странице.

- **Submit** (любой авторизованный) — пишет `<ID>.json` + `<ID>.{zip|pdf}` в `10_up` (имена в нормализованной форме `00001-TLIB`). Уникальность проверяется против `tlib.db`, `10_up`, `20_go`, `30_processing`.
- **Publish** (админ) — переносит пару json+файл из `10_up` в `20_go`, после чего отчёт обрабатывается обычным pipeline (см. ниже).
- **Reject** (админ) — переносит пару в `data.old/` с timestamp и пишет `<ID>_<ts>.err` с комментарием.

### Сайдкар-маркеры в 10_up

Помимо пар json+архив, в `10_up` могут лежать сайдкар-маркеры. **Pipeline их не сканирует** — их обрабатывает страница `/upload.html` и API загрузки:

- `<ID>.editmeta` — заявка является **правкой опубликованного** отчёта (`POST /api/upload/submit-edit`). Содержит `orig_id` (исходный опубликованный ID), `edited_by_id`, `edited_by_email`, `edited_at`. В списке `/api/upload/list` такая заявка помечается `is_edit: true` и (при смене шифра) `orig_id` (бейдж «ред. ← СТАРЫЙ-ID»). При **публикации** (`POST /api/upload/publish`): если новый код (`new_norm_id`) отличается от `orig_id` — в `20_go` автоматически создаётся `.delete`-триггер для старого ID (File Watcher удалит старые файлы и запись в БД), маркер удаляется из `10_up`. При **отклонении** (`POST /api/upload/reject`): маркер переносится в `data.old/` вместе с парой.
- `<ID>.delreq` — **запрос на удаление** опубликованного отчёта (`POST /api/upload/request-delete`, содержит причину и инициатора). Админ подтверждает (создаётся `.delete` в `20_go`) или отклоняет (маркер удаляется).

См. [API: загрузка отчётов](API.md#загрузка-отчётов-apiupload) и [Безопасность §8](SECURITY.md).

### Маркеры уведомлений `<ID>.notify`

При публикации отчёта через `/upload.html` создаётся файл-маркер `data.up/<ID>.notify` (в корне `data.up/`, содержимое — комментарий администратора). **Pipeline эти файлы игнорирует.** Их обрабатывает отдельная задача File Watcher (`process_pending_notifications` в `services/file_watcher/notify.py`): после того как отчёт реально опубликован в `data/`, она отправляет загрузившему письмо об итоге и удаляет маркер. Так письмо «опубликовано» приходит только по факту появления отчёта в БД, а не в момент нажатия «Опубликовать».

## Типы групп

Группа — набор файлов с одним ID (Шифр или Шифр-ДопШифр). Группировка выполняется по **нормализованному ID**: Шифр приводится к 5 цифрам с ведущими нулями, ДопШифр — к UPPERCASE. Благодаря этому разные написания одной карточки автоматически склеиваются в одну группу (например, `1-tst.json` и `00001-TST.zip` → группа `00001-TST`).

При загрузке файлов в `data.up/20_go/` pipeline определяет тип группы:

| Тип | Условие | Бэкап из data/ | Кэш | Валидация JSON | Пересборка БД |
|-----|---------|----------------|-----|----------------|---------------|
| **Полная** | JSON + (PDF или ZIP) | Все файлы группы | удаляется | да | да |
| **Только JSON** | JSON без PDF/ZIP, ТипФайла=null / нет поля; или ТипФайла=zip/pdf и нужный архив уже есть в `data/` | Только старый .json | не меняется | да | да |
| **Частичная** | PDF/ZIP без JSON, при наличии JSON в data/ | Только совпадающие расширения | удаляется | нет | нет |
| **Ожидает архив** | Только JSON, ТипФайла=zip/pdf, а файла `{id}.{тип}` нет в `data/` | — | — | — | — |

Если PDF/ZIP загружены без JSON и JSON отсутствует в `data/` — группа пропускается до следующего цикла.

Если JSON объявляет `ТипФайла`, но нужный архив ещё не доехал (режим «Ожидает архив») — JSON остаётся в `20_go/`, ничего не двигается. Сигнал для администратора: метрика «В очереди» в панели мониторинга и info-строка в логах.

### Дубликаты после нормализации

Если после нормализации в одной группе оказываются два файла с **одинаковым целевым именем** (например, `1-TST.json` и `00001-TST.json` — оба дают `00001-TST.json`), вся группа считается **ambiguous** и пропускается.

Файлы остаются в `data.up/20_go/`, в `logs/app.log` пишется WARNING:

```
[FILE_WATCHER] Группа 00001-TST пропущена: после нормализации обнаружены дубликаты
    для целевого имени 00001-TST.json: 1-TST.json, 00001-TST.json.
    Удалите лишний файл из data.up/20_go/, чтобы разблокировать обработку.
```

**Восстановление:** удалите один из дублирующихся файлов из `data.up/20_go/`. Группа будет обработана на следующем тике.

### Специальные триггеры

| Триггер | Формат | Действие |
|---------|--------|----------|
| **Пауза** | директория `data.up/pause/` | Остановить обработку до удаления директории |
| **Удаление** | `ШИФР.delete` или `ШИФР-ДОПШИФР.delete` в `data.up/20_go/` | Удалить запись из БД и файлы из data/ (создаётся вручную, через `/upload.html` → confirm-delete, или автоматически при публикации правки со сменой шифра) |
| **Пересборка** | `reindex.*` (любое расширение) в `data.up/20_go/` | Полная пересборка tlib.db из всех JSON в data/ |

## Stability-window (проверка готовности файлов)

Перед тем как группа попадёт в pipeline, File Watcher убеждается, что её файлы полностью дозалиты и не находятся в процессе синхронизации (GoogleDrive, сетевые ФС, копирование по SMB).

**Правила:**
- Каждый скан фиксирует `(size, mtime)` каждого файла в `data.up/20_go/`.
- Файл считается стабильным, если `(size, mtime)` **не менялись `FILE_WATCHER_STABILITY_CHECKS` последовательных сканов подряд**.
- Группа обрабатывается, **только если все её файлы стабильны**. Пока хотя бы один файл нестабилен — вся группа откладывается до следующего тика.
- При любом изменении `size` или `mtime` счётчик сбрасывается.

**Минимальная задержка обработки нового отчёта:** `FILE_WATCHER_CHECK_INTERVAL × FILE_WATCHER_STABILITY_CHECKS` — при значениях по умолчанию это **~2-3 минуты** после окончания синхронизации.

**Исключения (обрабатываются без задержки):**
- `.delete`-триггеры — файлы нулевого размера, всегда «готовы».
- `reindex.*` — триггер пересборки, обрабатывается до stability-фильтра.

**Побочный эффект:** если JSON и ZIP/PDF залиты одновременно, они автоматически склеиваются в одну `complete`-обработку (один цикл публикации БД вместо двух-трёх).

**Ожидание архива при разрыве синхронизации:** если JSON объявляет `ТипФайла=zip` (или `pdf`), но файла `{normalized_id}.{тип}` нет в `data/`, pipeline не классифицирует группу как «Только JSON» и не двигает JSON из `20_go/`. Группа ждёт именно тот тип архива, который объявлен в JSON, — даже если у карточки в `data/` лежит архив другого типа (смена типа требует загрузки нового архива нужного расширения). Это защищает от сценария, когда Drive-синхронизация доставляет JSON и ZIP с разрывом больше stability-window: до фикса JSON падал в `40_error/` с ошибкой «ТипФайла=zip, но архив отсутствует», пока ZIP добирался позже.

**Диагностика:** нестабильные группы выводятся в `logs/app.log` на уровне DEBUG:
```
[FILE_WATCHER] Нестабильные группы (ждём 3 одинаковых сканов): ['12345-а']
```

## Структура директорий

```
data.up/
├── (корень — файлы лежат, pipeline их не видит; здесь же маркеры <ID>.notify)
├── 10_up/          # Модерация: наполняется через /upload.html (pipeline не трогает)
├── 20_go/          # Точка входа pipeline — сюда кладут файлы для обработки
├── 30_processing/  # В обработке
├── 40_error/       # Ошибки + .err описания
└── pause/          # Создать для паузы (маркер-каталог)

data.new/                    # Успешно обработанные файлы

data/                        # Рабочие файлы отчетов

data.old/                    # Бэкапы с timestamp
```

## Требования к файлам

### Имена файлов

- С допшифром: `12345-а.json`, `12345-а.zip`, `12345-а.pdf`
- Без допшифра: `12345.json`, `12345.zip`, `12345.pdf`
- Допшифр: 1-5 символов (кириллица, латиница, цифры)

**Нормализация при обработке:** Pipeline автоматически нормализует имена — ведущие нули Шифра и регистр ДопШифра. Следующие написания эквивалентны и будут склеены в одну группу `00001-TST`:

- `1-TST.json` ≡ `00001-TST.json`
- `1-tst.zip` ≡ `00001-TST.zip`
- `00001-tst.pdf` ≡ `00001-TST.pdf`

В `data/` файлы всегда хранятся в нормализованной форме (`00001-TST.json`). При копировании из `30_processing/` имена автоматически приводятся к канонической форме.

**Канонизация поля ДопШифр внутри JSON:** после валидации, перед финальной проверкой БД, pipeline приводит поле `ДопШифр` в JSON к UPPERCASE (`canonicalize_json_dopshifr` в `file_operations.py`). Это гарантирует, что в `data/` и в БД значение всегда в верхнем регистре независимо от написания оператора (`"tst"` → `"TST"`). Если значение уже UPPERCASE или пустое — файл не перезаписывается.

### JSON схема

Файл должен соответствовать `assets/schema.json`.

**Обязательные поля:**
- `Шифр` (integer)
- `Год` (integer, 1950-2100)
- `МесяцС` (integer, 1-12)
- `МесяцПо` (integer, 1-12)

**Опциональные поля:**
- `ДопШифр` (string, max 5)
- `Маршрут`, `РайонОбщий`, `Район`
- `Автор`, `Город`, `Тип`, `ТипСудна`
- `КатегорияС`, `КатегорияПо`
- `Комментарии`
- `РазмерАрхива` (integer)
- `ТипФайла` ("zip" или "pdf")

**Пример:**
```json
{
  "Шифр": 12345,
  "ДопШифр": "а",
  "Маршрут": "По Байкалу",
  "Год": 2024,
  "МесяцС": 7,
  "МесяцПо": 8,
  "ТипФайла": "zip"
}
```

## Этапы валидации

### 1. Проверка кодировки

- Null bytes в строках
- Суррогатные пары Unicode
- Невалидные символы
- Время: ~1-5 мс

> Чтение JSON по всему приложению идёт через `services/json_io.py` (`read_json`, кодек `utf-8-sig`): UTF-8 BOM (`EF BB BF`) при наличии прозрачно срезается, поэтому легаси-отчёты, сохранённые в Windows-редакторах с BOM, читаются без ошибок и без конвертации файлов.

### 2. Проверка JSON по схеме

- Обязательные поля
- Типы данных
- Диапазоны значений
- Время: ~10-50 мс

### 3. Финальная проверка

- Генерация БД из всех файлов (data/ + новые)
- Проверка совместимости
- Если провал → весь батч в 40_error/

## Обработка ошибок

При ошибке валидации:
1. Файлы перемещаются в `data.up/40_error/`
2. Создается файл `GROUP_ID.err` с описанием

**Пример .err файла:**
```
============================================================
ОШИБКА ОБРАБОТКИ FILE WATCHER
============================================================
ID группы: 12345-а
Время: 2025-12-25 09:00:00 UTC
Причина: Ошибка валидации

------------------------------------------------------------
ДЕТАЛИ
------------------------------------------------------------
'invalid_year' is not of type 'integer'
```

**Восстановление:**
```bash
# Прочитать ошибку
cat data.up/40_error/12345-а.err

# Исправить JSON и повторить
mv data.up/40_error/12345-а.* data.up/20_go/
```

## Конфигурация

**config/database.py:**
```python
FILE_WATCHER_CHECK_INTERVAL = 60      # Интервал проверки (сек)
FILE_WATCHER_STABILITY_CHECKS = 3     # Сканов подряд без изменений → файл готов
FILE_WATCHER_BATCH_SIZE = 100         # Макс групп за цикл
AUTO_DELETE_DONE_FILES = False        # Хранить в data.new/
ALLOWED_FILE_EXTENSIONS = {'.json', '.zip', '.pdf', '.delete'}
REINDEX_TRIGGER_PREFIX = "reindex"    # Имя файла-триггера пересборки БД
```

## Логирование

### logs/app.log

```
[FILE_WATCHER] Цикл завершен: найдено=4, групп=2, успешно=2, ошибок=0
[FILE_WATCHER] Группа 00001-TST ожидает архив (ТипФайла='zip', файла 00001-TST.zip нет в data/)
```

Строка «ожидает архив» появляется каждый цикл, пока нужный архив не придёт. Это штатное состояние, не ошибка. Сигнал для администратора — метрика «В очереди» в панели мониторинга остаётся ненулевой.

### data.up/processing.log

```
2025-12-14 13:14:40 | 12345-а | SUCCESS | 3 files | data/ + done/
2025-12-14 13:15:12 | 99999   | ERROR | Validation failed | error/
```

## Мониторинг редких ошибок

Если файл прошел валидацию, но провалил финальную проверку БД:

```
[FILE_WATCHER] ⚠️ РЕДКАЯ ОШИБКА: N групп прошли валидацию, но провалили финальную проверку БД
```

**Возможные причины:**
- Дублирующиеся Шифр+ДопШифр между файлами
- SQLite-специфичные ошибки
- Системные ошибки (диск, права)
