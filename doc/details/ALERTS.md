# Email-уведомления администраторов (Alerts & Digest)

## Назначение

Система уведомляет администраторов о проблемах на сервере по двум каналам:

- **Немедленный алерт** — письмо при URGENT-событии (критическая ошибка, пустой диск и т.п.)
- **Ежедневный дайджест** — одно письмо в настраиваемое время (по умолчанию 20:00 МСК) с тремя секциями

---

## Архитектура

```
app_logger.critical(...)   → CriticalMailHandler → send_admin_alert()
send_admin_alert() напрямую                       → send_admin_alert()
                                                         ↓
                                               троттлинг in-memory
                                                         ↓
                                               SMTP в отдельном потоке → URGENT-письмо

daily_digest_task (фон) → parse_critical_log()
                        → StatsCollector.query()
                        → shutil.disk_usage()
                        → _collect_admin_emails()
                                         ↓
                               SMTP в asyncio.to_thread → Дайджест
```

## Уровни событий

| Уровень | Поведение |
|---------|-----------|
| `URGENT` | Немедленное письмо с троттлингом (1 письмо / `ALERT_THROTTLE_MINUTES`) |
| `ATTENTION` | Попадает в секцию «Требует внимания» ежедневного дайджеста |
| `INFO` | Попадает в секции «События» и «Статистика» дайджеста |

---

## Типы событий

### URGENT

| `event_type` | Человеческое описание |
|---|---|
| `DB_SWAP_FAILED` | Не удалось обновить БД из tlib-new.db |
| `DISK_LOW` | Занятость диска > `DISK_CRIT_PERCENT` (90%) **или** свободно < резерва при блокировке аплоада |
| `SERVER_ERROR_STORM` | Большое количество ошибок сервера подряд |
| `SECURITY_STORM` | Более `SECURITY_STORM_THRESHOLD` security-событий за окно |
| `FILE_WATCHER_CRASHED` | File Watcher перестал работать |
| `DB_WATCHER_CRASHED` | DB Watcher перестал работать |
| `SMTP_CRITICAL` | Недоступен SMTP для отправки писем |
| `ZIP_BOMB_DETECTED` | Обнаружена потенциальная zip-бомба |

### ATTENTION (в дайджесте)

| `event_type` | Описание |
|---|---|
| `BATCH_ERROR` | Отчёт попал в 40_error |
| `PATH_TRAVERSAL_ATTEMPT` | Попытка path traversal атаки |
| `RATE_LIMIT_EXCEEDED` | Превышен rate limit |
| `ARCHIVE_SIZE_EXCEEDED` | Запрошен слишком большой архив |
| `DISK_WARN` | Занятость диска > `DISK_WARN_PERCENT` (75%) |
| `STALE_QUEUE_FILES` | Файлы в 20_go старше суток |
| `INVALID_REQUEST` | Некорректные запросы |

## Структура письма-алерта

```
Тема: [<домен>] СРОЧНО: <краткое описание>

<Человеческое описание события>
Что делать: <рекомендация>
[При необходимости: событие повторилось N раз(а)]

--- Технические детали ---
event_type=DB_SWAP_FAILED
time=2026-06-12 10:03:11 UTC
error_type=OperationalError
error="database is locked"
```

---

## Структура дайджеста

```
Тема: [<домен>] Дайджест 12.06 — 2 проблемы требуют внимания
      (или «— всё в порядке» если ATTENTION-секция пуста)

tLib дайджест 12.06.2026

ТРЕБУЕТ ВНИМАНИЯ          <- опускается если пусто
- <описание проблемы 1>
- <описание проблемы 2>

СОБЫТИЯ
- Файлов в очереди обработки: 0.

СТАТИСТИКА
- Уникальных посетителей за сутки: 1240.
- Поисковых запросов: 580, скачиваний: 43.
- Диск: занято 61% от 200 ГБ, свободно 78.0 ГБ.

--- Технические детали ---  <- только при наличии проблем
  RATE_LIMIT_EXCEEDED: 42
  PATH_TRAVERSAL_ATTEMPT: 3
```

`<домен>` — это `MAIL_SUBJECT_PREFIX` (`config/security.py`): домен, извлечённый из `SITE_URL`
(`data.secret/.env`). Один и тот же код работает для любого хостинга — прод отправит
`[tlib.ru] ...`, тестовый сервер на Tailscale Funnel — `[hostname.tailnet-name.ts.net] ...`.
Если `SITE_URL` не задан или домен не распознан — используется заглушка `[tLib-unknown-host]`.
Этот же префикс используется во всех остальных письмах приложения (уведомления о загрузке,
публикации, удалении отчётов, вход по magic link), не только в алертах и дайджесте.

## Троттлинг алертов

- Не более 1 письма на `event_type` за `ALERT_THROTTLE_MINUTES` (30 мин).
- Повторные события за окно не теряются — счётчик сохраняется.
- В следующем письме указывается «событие повторилось N раз».
- Throttle хранится in-memory: при рестарте сбрасывается.

**Security-шторм:** при превышении `SECURITY_STORM_THRESHOLD` security-событий за окно отправляется единственное URGENT-письмо «возможная атака» (тоже с троттлингом).

---

## Ежечасная проверка диска

Фоновая задача `daily_digest_task` раз в час вызывает `shutil.disk_usage()`. При занятости диска выше `DISK_CRIT_PERCENT` (90%) уходит URGENT-алерт `DISK_LOW`. Повторы гасятся троттлингом.

## Немедленный алерт при блокировке аплоада

При блокировке загрузки пользователем (507, `disk_allows_upload` → False) роутер загрузки (`upload_router.py:_disk_full_response`) немедленно вызывает `send_admin_alert("DISK_LOW", ...)`. Алерт срабатывает по обоим условиям (`disk_critical` ≥ 90% или `disk_reserve` < 4 ГБ) и по тому `UPLOAD_STAGING_DIRECTORY`, который реально проверяется.

Бакет троттлинга общий с почасовой проверкой (`ALERT_THROTTLE_MINUTES = 30`): если почасовая уже отправила письмо, немедленный подавляется, и наоборот. `/api/upload/status` алерт не шлёт.

---

## Уведомление о старте сервера

При каждом запуске приложения (lifespan) уходит письмо `SERVER_STARTED` со временем, числом отчётов в базе и портом. Позволяет заметить неожиданный рестарт.

## Настройка в панели администратора

В карточке 6 «Управление правами администраторов» (`/admin`):

- Поле «Дайджест отправляется в ЧЧ:ММ (МСК)» с кнопкой «Сохранить»
- Кнопка «Отправить тестовое письмо»

Настройки хранятся в таблице `app_settings` (auth.db), ключ `digest_send_time`.

**API (только для авторизованных администраторов):**

- `GET /api/admin/settings` → `{"digest_send_time": "20:00"}`
- `POST /api/admin/settings` с `{"digest_send_time": "HH:MM"}`
- `POST /api/admin/test-email` → отправляет тестовое письмо всем администраторам

## Константы конфигурации (`config/alerts.py`)

| Константа | Значение по умолчанию | Описание |
|-----------|----------------------|---------|
| `ALERT_THROTTLE_MINUTES` | 30 | Окно троттлинга алертов |
| `SECURITY_STORM_THRESHOLD` | 200 | Порог security-событий для шторм-алерта |
| `DIGEST_DEFAULT_SEND_TIME` | `"20:00"` | Дефолт времени отправки (МСК) |
| `DIGEST_TIMEZONE_OFFSET_HOURS` | 3 | Смещение МСК от UTC |
| `DISK_WARN_PERCENT` | 75 | Порог предупреждения о диске (дайджест) |
| `DISK_CRIT_PERCENT` | 90 | Порог критического состояния диска (URGENT) |

---

## Получатели

Все письма уходят на адреса:

1. `ROOT_ADMIN_EMAIL` из `data.secret/.env`
2. Все активные пользователи с ролью `admin` в `auth.db`

Список собирается при каждой отправке через `services/alerts/recipients.py` — изменения применяются без рестарта.

---

## Добавление нового типа события

1. Добавить в `ALERT_LEVELS` (`config/alerts.py`) уровень события.
2. Добавить в `ALERT_DESCRIPTIONS` человеческое описание и рекомендацию.
3. В нужном месте кода вызвать `send_admin_alert("MY_EVENT", **data)`.

Для CRITICAL-уровня логгера (событий через `app_logger.critical(...)`) — ничего добавлять не нужно: `CriticalMailHandler` отправит письмо автоматически.
